# 01 · 架构说明

---

## 一、三层结构

```
┌─────────────────────────────────────────────────────────┐
│  外壳 APK（普通 App，无需 root）                          │
│  ├─ 解密 assets 里的资源到 /data/local/tmp               │
│  ├─ 刷驱动（su insmod）                                  │
│  ├─ 启动/停止下面两个进程（su）                           │
│  └─ 提供设置界面（类别开关、价格挡位、驱动版本选择）        │
└─────────────────────────────────────────────────────────┘
                          ↓ su 启动
┌──────────────────────────┐      ┌──────────────────────────┐
│  采集端（C，root）         │      │  绘制端（Java/dex，root）  │
│  ├─ 通过驱动读游戏内存      │      │  ├─ 读 esp.txt            │
│  ├─ 遍历 Actor 数组        │ ───→ │  ├─ 算标签布局            │
│  ├─ 分类（人/机/容器/物资） │ esp  │  ├─ 用 SurfaceFlinger     │
│  ├─ 投影算屏幕坐标         │ .txt │  │   直接画 overlay       │
│  └─ 写出 esp.txt          │      │  └─ 处理触摸事件          │
└──────────────────────────┘      └──────────────────────────┘
           ↑ 读内存
┌──────────────────────────┐
│  内核模块（LKM）           │
│  └─ hook __NR_reboot      │
│     提供 read/find_proc/  │
│     module_base 三个能力   │
└──────────────────────────┘
```

**关键设计**：采集端和绘制端**只通过一个文本文件通信**，完全解耦。

好处：

- 任意一端崩了，另一端不受影响（绘制端会继续画上一帧）
- 可以单独替换（比如只换绘制端改 UI，采集端不动）
- 调试方便（`cat esp.txt` 就能看到采集端到底读到了什么）

## 二、数据流：esp.txt 格式

采集端每帧（约 8ms）原子地重写这个文件（写 `esp.tmp` 再 `rename`）。

```
pid=20722                                   ← 游戏进程号
ts=1792926263521                            ← 时间戳（ms）
cnt=1255                                    ← Actor 数组元素数
local=-16630,4964,2769                      ← 本地玩家世界坐标

a=cx y w h dm kind                          ← 方框（可选，现在基本不用）
t=kind cx y dm cls ua tf100 wp 甲 头 名字     ← 标签 ★主要数据
s=x1 y1 x2 y2                               ← 骨骼线段（每行一段）
pl=N                                        ← cull 内真人数
p260=N                                      ← 260m 内真人数
realpl=N                                    ← 全图人数（GameState，未打通）
enz=... aiz=... zspan=... dz=... enN=.. aiN=.. enc4=N   ← 加密判定素材
ace=N 文件名                                 ← ACE 目录 5 秒内被写过的文件数
SELF_LA h=3 a=4                             ← 自己的头甲（调试用）
```

### `t=` 行字段（11 个，绘制端按位置解析）

```
t=%d %.0f %.0f %d %s %u %d %s %d %d %s
  │   │    │   │  │   │  │  │  │  │  └─ tp[10] 玩家名字（UTF8，空格换成 _，无则 "-"）
  │   │    │   │  │   │  │  │  │  └──── tp[9]  头盔等级（0=没穿）
  │   │    │   │  │   │  │  │  └─────── tp[8]  护甲等级（目前恒 0，见 06）
  │   │    │   │  │   │  │  └────────── tp[7]  手持物/实例名
  │   │    │   │  │   │  └───────────── tp[6]  tf*100（恒 4000）
  │   │    │   │  │   └──────────────── tp[5]  0x1290 枚举（1/2/3）
  │   │    │   │  └──────────────────── tp[4]  类名
  │   │    │   └─────────────────────── tp[3]  距离（米）
  │   │    └─────────────────────────── tp[2]  屏幕 Y
  │   └──────────────────────────────── tp[1]  屏幕 X
  └──────────────────────────────────── tp[0]  kind（0真人 1人机 2容器 3物资 4人机玩家）
```

> ⚠️ **曾经在这踩过坑**：名字是 `tp[10]`，曾误写成 `tp[11]` + `length>=12`，
> 条件永远不成立 → 名字一个都不显示。

### `kind` 分类规则

| kind | 含义 | 判定 |
|---|---|---|
| 0 | 真人玩家 | `actor+0x330`(PlayerState) 非空，**或**玩家模型且非 AI 类名 |
| 1 | 人机 | AI 模型且 `ua != 2` |
| 2 | 容器/盒子 | 类名命中 `BOX_KW`/`CONT_KW`（Box/Bag/Case/Safe/DeathBox…） |
| 3 | 地上物资 | 类名命中 `ITEM_KW` 且含 `_Uam_C` |
| 4 | 人机玩家 | AI 模型但 `ua == 2`（被玩家控制） |

## 三、采集端（`src/C/paradise_fast100.c`）

### 主循环

```c
syscall(reboot, M1, M2, 0x1234567, &FD);   // 拿驱动 fd
ioctl(FD, P_FIND_PROC, &fi);               // 找游戏 pid
ioctl(FD, P_MODULE_BASE, &mo);             // 拿 libUE4.so 基址
GN = base + GOFF_GNAMES;                   // ★ 初始化 GNames，否则类名全解析失败

for (;;) {
    world = r64(base + G_WORLD);
    level = r64(world + 0x30);
    actors = r64(level + 0x98);
    cnt = r32(level + 0xa0);

    rd(actors, BUF, cnt * 8);              // ★ 必须批量读，逐个读会失败

    for (i = 0; i < cnt; i++) {
        actor = BUF[i] & MASK;
        读 actor 前 0x440 字节到 blk（一次读，减少 ioctl 次数）
        分类 / 过滤 / 投影 / 写 t= 行
    }

    写 esp.tmp → rename 成 esp.txt
    usleep(8000);                          // 目标 120fps
}
```

### 关键优化

| 优化 | 原因 |
|---|---|
| 一次读 `blk[0x440]` | 分类需要 0x158/0x330/0x42c/0x1290 等多个字段，一次读完比分 5 次读快 5 倍 |
| 批量读 Actor 数组 | 逐个读会全部失败（驱动限制） |
| 只有进入绘制范围才读骨骼 | 骨骼要读 `mesh+0x700` 再算变换，代价高 |
| `OFF_VEST` 等自标定只扫一次 | 全扫代价大，学到就固定 |

### 体积与性能

- 源码约 1000 行，编译后 **33 KB**
- 对局中（cnt≈1500）单帧约 **8ms**

## 四、绘制端（`src/Java/Ov50.java`）

### 为什么用 `app_process` 跑 dex

```bash
CLASSPATH=/data/local/tmp/.c/o.dex app_process /data/local/tmp Ov50 2414 1080 0 0
                                        ↑ 类名    ↑ W  H  X Y
```

- 不需要装 App、不需要签名
- 进程名可以伪装
- root 权限下拿 SurfaceFlinger 更容易

### 画布从哪来

```java
// 反射创建 Surface / SurfaceControl，然后 lockCanvas 直接画
Surface surface = ...;
Canvas c = surface.lockCanvas(null);
c.drawRect / drawBitmap / drawLine ...
surface.unlockCanvasAndPost(c);
```

**所有 `android.*` 都是反射调用**，编译期不需要 android.jar 的实现。

### 绘制顺序

```
确保透明（PorterDuff CLEAR）
  ↓
左上角：加密状态
  ↓
顶部中间：全图人数 / 260m 内人数
  ↓
方框（角色）
  ↓
骨骼连线
  ↓
标签（角色/容器/物资）
  ↓
菜单面板（如果展开）
```

### 两个关键机制

**① keepAlive 防抖**

容器/物资 streaming 抖动时，用上一帧坐标补画一次：

```java
String key = kind + "|" + 实例名 + "|" + 类名;   // ★ 绝对不能带屏幕位置
KEEP_MS = 250;
// 补画一次就把时间戳标成过期，避免连续补
```

**② 整帧 try/catch**

```java
for (int f = 0; ; f++) {
  try { ...整帧... }
  catch (Throwable th) { System.out.println("[!] frame " + f + " 异常"); }
}
```

> 没有这层，任何单帧异常都会让绘制线程死掉 = 用户看到的「闪退」。

## 五、外壳 APK

### 它做的三件事

1. **解密资源**：`assets/*.bin` 是 AES-256-CBC 加密的，运行时用内置 KEY/IV 解密到 `/data/local/tmp`
2. **刷驱动**：按内核版本选 `drv_*.bin`，解密后 `su -c "sh ..."`
3. **起停进程**：`su -c` 执行 start_esp.sh 里那些命令

### 为什么资源要加密

APK 会被扫描/分析，明文放二进制和表容易被识别。加密后 asset 名字也不带语义（`p`、`o.dex`、`drv61.bin`）。

## 六、命名约定

| 名字 | 含义 |
|---|---|
| `paradise_fastNN.c` | 采集端源码，NN 是迭代号 |
| `OvNN.java` | 绘制端源码，NN 是迭代号 |
| `.c/p` | 设备上的采集端二进制（名字故意短、无意义） |
| `.c/o.dex` | 设备上的绘制端 dex |
| `.c/o.log` / `.c/p.log` | 两端日志 |
| `esp.txt` | 通信文件 |
| `ov_kill` | 绘制端的自杀标记文件 |

> 采集端和绘制端跑起来后 **cmdline 会被抹成 `kworker`**，
> 所以找进程只能靠 `readlink /proc/*/exe`，不能靠 `ps` 的名字。
