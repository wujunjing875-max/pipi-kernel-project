## v3-ua-fix-2026-10-26（修复：真人被画成人机）

**现象**：附近真人被绘制成人机颜色/标签。

**根因**（现场实测）：`actor+0x1290` 的分类枚举真实取值是
```

```
原代码 `else if(modelAI) kind = (ua==2) ? 4 : 1;` 把 **ua==2 的真人**判成 `kind=4`（人机玩家），

**修改**（`src/C/paradise_fast100.c` 分类块）：

```c
else if(modelAI)           kind = 1;   // 纯人机
else                       kind = 0;
```

**验证**：`tools/dump_chars.c` 现场抓到的真值表（self ua=3 / 真人 ua=2 / 人机 ua=1）。

**产物**：`D:/WORKAI/ANQU/tpen_build/p_v3`（md5 c255d492…，与旧 bin 8e1e6184… 不同）

## v4-type-fix-2026-10-26（纠正：真人被误判成特遣人机）

**用户实测反馈**：刚被一个真人玩家击杀，那个玩家被系统判成了「特遣人机」。

**我的上一版结论是错的。** v3 之后我写"特遣 = `0x614==23`"，但
**自己和真人玩家的 `0x614` 同样是 23**，只有人机内部才是 23/4 的区别。

正确规则（两个字段必须同时看）：

| 组合 | 类别 |
|---|---|
| `0x154 == 50` | 玩家类（自己 / 远端真人） |
| `0x154 == 24 && 0x614 == 23` | 特遣人机 |
| `0x154 == 24 && 0x614 == 4` | 普通人机 |

RC 原判据 `0x154==50 && 0x614==23` 本来是对的，我不该拆开只用一半。

**代码修改**（`src/C/paradise_fast100.c`）：
```c
uint32_t t154 = r32(a + 0x154);   // 50=玩家类  24=人机类
uint32_t t614 = r32(a + 0x614);   // 人机内：23=特遣 4=普通

if(t154==50 || pst || ua==2 || ua==3)  kind = 0;          // 玩家类
else if(modelAI)                        kind = (t614==23) ? 4 : 1;
else                                    kind = 0;
```

**产物**：`D:/WORKAI/ANQU/tpen_build/p_v4`（md5 f4fd51f6…），已部署。

**教训**：差分扫描找出"能区分 A 和 B 的字段"后，必须再验证它在**其它类别**上的取值，
否则会把"和 A 同类的第三方"也拉进来。这次就是漏了"真人玩家的 0x614 也是 23"。

## v6-proxy-decrypt-2026-10-26 / v7-proxy-guard-2026-10-26（★ 加密破解）

## 2026-10-26 02:40 状态字段改独立行（关键修复）

**根因**：绘制端解析 esp.txt 是按"行首键名"匹配的：

**修法**：改成各自独立成行输出：

```

enc5=0
enc4=0
fake=1
undrawn=0
```
