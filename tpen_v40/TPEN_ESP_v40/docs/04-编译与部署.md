# 04 · 编译与部署

> 这一份是「换电脑后怎么把东西跑起来」的操作手册。
> 三样东西要编译：采集端（C）、绘制端（Java→dex）、外壳 APK。

---

## 〇、先改路径（换电脑第一步）

工程里有多处**写死的绝对路径**，换机器必须先改：

| 文件 | 写死的内容 |
|---|---|
| `src/apk/pack.sh` | `JDK=/d/WRAI/REA/.tools/jdk21-extract/jdk-21.0.12+1`、`SDK`、`AAPT`、`D8`、`APKSIGNER` |
| `tools/start_esp.sh` | 无（全用 `/data/local/tmp`，安全） |
| 编译命令（见下） | `NDK` 路径 |

**建议**：新建一个 `env.sh` 统一放路径，其它脚本 source 它。

```sh
# env.sh 示例
export NDK=/path/to/android-ndk-r26d
export JDK=/path/to/jdk-21
export ANDROID_SDK=/path/to/android-sdk
```

## 一、编译采集端（C → aarch64 可执行）

### 命令

```bash
NDK=/path/to/android-ndk-r26d
BIN=$NDK/toolchains/llvm/prebuilt/windows-x86_64/bin
SYSROOT=$NDK/toolchains/llvm/prebuilt/windows-x86_64/sysroot

"$BIN/clang.exe" \
  --target=aarch64-linux-android21 \
  -O2 -fPIE -pie \
  --sysroot="$SYSROOT" \
  -o out/paradise_fast100 \
  src/C/paradise_fast100.c \
  -lm
```

### 几个关键点

| 参数 | 为什么必须 |
|---|---|
| `--target=aarch64-linux-android21` | 目标架构 + API 级别（21 足够，用不到新 API） |
| `-fPIE -pie` | Android 10+ 强制要求位置无关可执行，否则跑不起来 |
| `--sysroot=...` | 用 NDK 自带的 bionic 头文件，不能用宿主机 glibc |
| `-lm` | `sqrtf` / `fabsf` 等数学函数 |

**Windows 下注意**：要设 `TEMP`/`TMP` 到不含空格和中文的路径，
否则 clang 可能因为临时目录问题失败：

```bash
TEMP=/d/tmp TMP=/d/tmp "$BIN/clang.exe" ...
```

### 产物验证

```bash
file out/paradise_fast100
# 期望：ELF 64-bit LSB pie executable, ARM aarch64
```

大小应在 **30~35 KB** 左右。如果只有几 KB，说明编译时某个 `-O2` 被漏了或者源文件没读全。

## 二、编译绘制端（Java → dex）

绘制端是**没有 Android SDK 依赖**的纯 Java（全靠反射调 `android.view.Surface` 等），
所以可以用普通 `javac` + `d8` 编译，最后用 `app_process` 直接跑。

### 步骤

```bash
# 1. javac 编译（需要 android.jar 提供编译期符号）
"$JDK/bin/javac" \
  -source 8 -target 8 \
  -bootclasspath "$ANDROID_SDK/platforms/android-34/android.jar" \
  -d build/jcls \
  src/Java/Ov50.java

# 2. d8 转 dex
"$ANDROID_SDK/build-tools/34.0.0/d8" \
  --release --min-api 21 \
  --output build/dex \
  build/jcls/**/*.class
```

### 为什么用 `app_process` 而不是装 App

```
CLASSPATH=/data/local/tmp/.c/o.dex app_process /data/local/tmp Ov50 2414 1080 0 0
```

- 不需要签名、不需要装 App
- 进程名可控（可以伪装成别的）
- 直接用 root 权限跑，拿 SurfaceFlinger 的 surface 更简单

> 绘制端里所有 `android.*` 调用都是**反射**的（`Class.forName` + `Method.invoke`），
> 这样编译期不需要 android.jar 里的具体实现，运行期靠系统提供。

## 三、打包外壳 APK

`src/apk/pack.sh` 是一个纯 shell 的打包脚本，流程：

```
aapt2 compile/link  →  生成带资源的 unsigned.apk
javac               →  编译 Main.java
d8                  →  Main.class → classes.dex
aapt add            →  把 classes.dex 塞进 apk
zipalign            →  对齐
apksigner           →  签名
```

### 资源是加密的

`srcfiles/` 里的东西（采集端二进制、dex、表、图集、驱动）会被 **AES-256-CBC** 加密后
放进 `assets/`，运行时由 `Main.java` 解密到 `/data/local/tmp`。

```sh
KEY=...   # pack.sh 里的十六进制 key
IV=...
openssl enc -aes-256-cbc -K "$KEY" -iv "$IV" -in srcfiles/p -out assets/p.bin
```

**换机器不用改 KEY/IV**，保持原值即可。

### ⚠️ pack.sh 的两个大坑（务必先读）

1. **不能用 `rm -rf build`**
   这个目录文件数会超过 20，被沙箱/安全删除策略**静默拦截**——
   脚本不报错但没删掉，旧 class 残留导致 d8 报 `Invalid output: build\dex`。
   正确写法：

   ```sh
   mkdir -p build/jcls build/dex
   find build -name '*.class' -delete 2>/dev/null || true
   find build -name '*.dex'   -delete 2>/dev/null || true
   ```

2. **shell 脚本不能是 CRLF**
   Windows 上 Python `io.open(p,'w')` 默认会把 `\n` 转成 `\r\n`。
   改完 `.sh` 后一定要：

   ```bash
   sed -i 's/\r$//' pack.sh
   ```

   否则 `rm -rf build` 实际删的是 `build\r`，同样导致后面全乱。

## 四、部署到设备

### 4.1 一次性部署（手动）

见 `README.md` 的「快速开始 1」，核心就是 push 12 个文件 + 设权限。

### 4.2 一键启动脚本

`tools/start_esp.sh`：

```sh
#!/system/bin/sh
D=/data/local/tmp
C=$D/.c

# 1) 让旧 overlay 自杀（通过标记文件，因为进程名被伪装成 kworker 找不到）
touch $D/ov_kill; sleep 1; rm -f $D/ov_kill

# 2) 杀旧采集端（cmdline 被抹成 kworker，只能扫 /proc/*/exe）
for d in /proc/[0-9]*; do
  e=$(readlink $d/exe 2>/dev/null)
  case "$e" in *"/.c/p"*) kill -9 ${d#/proc/} ;; esac
done

# 3) 驱动（已加载会失败，忽略）
sh $C/drv.sh > $C/drv.log 2>&1

# 4) 绘制端
setsid sh -c "CLASSPATH=$C/o.dex exec app_process $D Ov50 2414 1080 0 0 > $C/o.log 2>&1" < /dev/null &
sleep 4

# 5) 采集端
setsid sh -c "exec $C/p > $C/p.log 2>&1" < /dev/null &
sleep 3
```

### ⚠️ 为什么必须用 `setsid`

`su -c "nohup xxx & "` 在 su 退出时**会连子进程一起收掉**，
表现就是「命令说启动了，但 `ps` 里没有」。必须：

```sh
setsid sh -c "exec xxx > log 2>&1" < /dev/null &
```

## 五、停止与清理

```bash
# 停绘制端（它自己会检查这个文件并 exit）
adb shell 'su -c "touch /data/local/tmp/ov_kill"'

# 停采集端（cmdline 被抹，只能按 exe 链接找）
adb shell 'su -c "for d in /proc/[0-9]*; do e=\$(readlink \$d/exe 2>/dev/null); case \"\$e\" in *\"/.c/p\"*) kill -9 \${d#/proc/};; esac; done"'

# 全部清理
adb shell 'su -c "rm -rf /data/local/tmp/.c /data/local/tmp/esp.txt /data/local/tmp/glyph.* /data/local/tmp/ov_*"'
```

## 六、调试入口

| 想看的 | 命令 |
|---|---|
| 采集端有没有崩 | `cat /data/local/tmp/.c/p.log` |
| 驱动加载情况 | `cat /data/local/tmp/.c/drv.log`、`dmesg \| grep -i paradise` |
| 绘制端出帧 | `grep "frame " /data/local/tmp/.c/o.log \| tail -3` |
| 绘制端异常（被吞掉的） | `grep "异常" /data/local/tmp/.c/o.log` |
| 当前数据 | `cat /data/local/tmp/esp.txt` |

**绘制端每帧异常都会被 try/catch 吞掉并打印 `[!] frame N 异常`**，
所以「看起来没崩但卡住」的时候，先 grep 这个。

## 七、性能参考

| 场景 | 采集端 | 绘制端 |
|---|---|---|
| 大厅（cnt≈90） | — | 30~40 fps |
| 对局（cnt≈1500） | 8ms/帧 | 45~57 fps |

如果 fps 掉到 30 以下，先看是不是场景里 actor 特别多，
或者绘制端 `keepAlive` 缓存爆了（见源码里 `pvN >= 200` 的重置逻辑）。
