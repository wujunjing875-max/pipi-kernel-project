> 打包时间：2026-10-26 03:35
> 目标游戏：`com.tencent.mf.uam`（暗区突围，UE4）
> 测试机：PJF110 / Android 16 / `6.1.118-android14-O64646`

## 一、一句话现状

**能用，而且解决了原始工程的头号难题（账号被风控加密时画不出真人）。**
真坐标从 `SGCharacterRepProxy` 系列里取，纯读、不写内存、不断点。
**唯一遗留问题是"延迟"**：加密玩家的坐标在小范围里更新很慢（实测 0.1~24Hz，因玩家而异），
已经在应用层用插值/预测做了缓解，但无法根治。

## 三、换电脑 3 步

### 1. 改路径

```bash

ANDROID_JAR= .../platforms/android-34/android.jar

```

### 2. 编译

```bash

```

### 3. 部署

```bash
bash deploy.sh 61          # 61 = 内核 6.1；其他见 drivers/ 目录名
```

脚本会：刷驱动 → 推文件 → 启动采集端+绘制端 → 打印状态。

**验证**：

```bash
adb shell "su -c 'grep -E \"^enc3=|^undrawn=|^drawn=\" /data/local/tmp/esp.txt'"
# enc3=1 表示当前账号处于加密态；undrawn=N 表示有 N 个真人取不到坐标没画
```

## 四、架构与数据流

```
[内核驱动 LKM]  hook __NR_reboot，提供 P_READ_PHYS
      ↓ ioctl 读内存（只读）
[采集端 p]      遍历 actor → 分类 → 算屏幕坐标 → 写 /data/local/tmp/esp.txt
      ↓ 文本文件（完全解耦）
[绘制端 dex]    app_process 跑 Java，SurfaceFlinger 直接画叠加层 → 读 esp.txt
```

**esp.txt 关键行**（绘制端按"行首键名"解析，字段必须在行首！）

```
F <帧号>
S x y z                     自机位置
pl= / p260= / drawn=        人数统计
pdt=<ms>                    代理坐标实测更新间隔（中位数）
enc3=<1|0|-1>               1=加密 0=正常 -1=未知
enc5=<n>                    本帧通过代理修正的坐标数
fake=<n>                    玩家类中被混淆坐标的个数
undrawn=<n>                 加密但画不出来的真人数
t=<kind> <x> <y> <dm> <类名> <ua> <tf> <手持> <甲> <头> <名字>
s= x1 y1 x2 y2              骨骼线段
```

## 五、偏移表（2026-10-26 实测，★ = 本项目新发现）

### 5.1 UE4 基础链

```c
G_WORLD  = base + 0xFBEEE10   → r64 得 world
level    = r64(world + 0x30)
actors   = r64(level + 0x98)   // 必须整块批量读，逐个读会失败
count    = r32(level + 0xA0)   // 实测 800~1700
```

### 5.2 投影矩阵（★ 已定位）

```c
pov   = r64( r64( r64(base + 0xFBA6F20) + 0x20 ) + 0x2A0 );   // G_ENGINE 链
float M[16]; rd(pov, M, 64);

w  = x*M[3] + y*M[7] + z*M[11] + M[15];   // w<=1 表示在身后
sx = 1207 + 1207*(x*M[0]+y*M[4]+z*M[8] +M[12])/w;
sy =  540 -  540*(x*M[1]+y*M[5]+z*M[9] +M[13])/w;
```

> 注意：**不要**用 `cam_mgr+0x1100` 的 POV 位置当相机（实测比自机低 71cm，是"视线缓存"）。
> 矩阵已含相机位置/朝向/FOV，站蹲趴开镜全部自动正确。

### 5.3 角色

```c
root      = r64(actor + 0x158);   pos = rd(root + 0x154)      // 世界坐标（加密态为假值）
ps        = r64(actor + 0x330);   name = ps + 0x440/0x450/0x6F8/0x718  // UTF16 FString
mesh      = r64(actor + 0x370);   bones = r64(mesh+0x700), 数量 r32(mesh+0x708)  // 实测 109
                                  CTW 平移 = mesh + 0x8C0
ua        = r32(actor + 0x1290)    // 1=人机 2=远端玩家(真人/伪装者) 3=自己
t154      = r32(actor + 0x154)     // 50=玩家类  24=人机类
t614      = r32(actor + 0x614)     // 人机内部：23/4（★ 不专属特遣，别乱用）
头盔      = r32(actor + 0x1F80)    // 1~6，0=没穿
```

**分类规则（现用）**

```c
if (t154==50 || 有PlayerState || ua>=2)  kind = 0;   // 玩家（真人/伪装者 不做区分）
else if (类名含AICharacter)              kind = 1;   // 人机
else                                     kind = 0;
// 排除自己只能用"与自己坐标重合(dm==0)"，不能用 ua==3
```

### 5.4 ★ 代理体（加密破译的核心）

```c
// 在 actor 数组里找类名含 "FastRepProxy" 的对象
owner = r64(proxy + 0x108);       // 指回它所对应的 BP_UamCharacter_C
// 坐标（三份，互不相同！）
A: rd(proxy + 0x314)    // 有的玩家是静止值/全 0
B: rd(proxy + 0x330)    // 有的玩家约 24Hz 高频更新 ★ 最常用
C: proxy + 0x11050      // ★ 部分玩家有第三份，但偏移不固定、可能是垃圾
```

⚠️ **偏移不可移植**：`0x11050` 这类位置是堆相对地址，**每个玩家不同**，不能写死。

## 六、四个解密开关（面板里，护甲条下面）

| 开关 | 文件 | 通道 | 平滑策略 | 说明 |
|---|---|---|---|---|
| 解密1 | `ov_dec.txt` | `+0x314` | 速度外推（1.2s 窗口） | 平滑但会过冲 |
| 解密2 | `ov_dec2.txt` | `+0x330` | 指数插值 τ=0.08s | 接近直出 |
| 解密3 | `ov_dec3.txt` | `+0x11050` | 指数插值 τ=0.25s | 平滑不过冲 |
| **解密4** | `ov_dec4.txt` | **三路自动选** | 插值 τ=0.12s | **推荐** |

解密4 的选路逻辑（`src/C/paradise_fast100.c` 里搜 `主动三路`）：

```
每帧读三路 → 各自统计变化次数 + 记录最近变化时间
每 60 帧结算：变化次数最多的胜出；全静止则取最近变过的那路；都没变过用 0x330
```

**只开一个！** 多个同时开时以"解密4 > 解密3 > 解密2 > 解密1"优先级生效。

## 七、加密机制研究结论（重要，避免重复劳动）

### 7.1 加密后是什么样

```
真人 actor 的 root+0x154 / mesh+0x8C0 全是假值：z ≈ -500（地下），多个玩家挤在同一小块
PlayerState 仍然有效，但里面没有坐标
骨骼数组 109 根正常，但位置跟着假 CTW 一起错
```

### 7.2 真值在哪

**只在 FastRepProxy 里**，且三份数据不完全一样（实测两两"同值比例 0%"）：

| 通道 | 实测刷新率 | 备注 |
|---|---|---|
| `+0x314` | 常见完全静止 | 值稳定但可能陈旧 |
| `+0x330` | 实测有玩家 **118/250（≈24Hz）** | 最活跃 |
| `+0x11050` | 部分玩家是 `nan` 垃圾 | 偏移不可移植 |

**哪路"活"因玩家而异**——所以必须有解密4 这种自动选路。

### 7.3 已经排除的坐标源（别再找了）

| 位置 | 结论 |
|---|---|
| actor 本体 0~0x2400 | 无世界坐标（变化快的是角度/进度标量，如 +0x1728） |
| 角色 40 个子组件 | 坐标候选 **0 个** |
| PlayerState / ArmorMgr | 无坐标 |
| 模块 `.so` 数据段（36.8MB） | 按值扫 0 命中 |
| 可读匿名堆（400MB） | 按值扫 0 命中 |

### 7.4 为什么"纯算法解密"不可能

加密后的坐标是**塌缩**的（多玩家映射到同一小区域），信息已丢失，不存在可逆变换。
RC 那条链能解，是因为它读的是**另一份真值副本**，不是算出来的。

## 八、已知限制

1. **延迟无法根治**：数据源本身低频（0.1~24Hz）。插值/外推只能缓解。
2. **僵尸 actor**：部分加密玩家只有空壳（内存全静止、无代理），取不到坐标 → `undrawn` 计数。
3. **代理未同步**的玩家会被跳过（宁可不画也不画错位置）。
4. **护甲等级**未找到（只有头盔 `0x1F80` 有效）。
5. **全图人数**未打通（`GameState.PlayerArray` 未定位）。
6. 特遣人机识别：`0x614==23` **不专属特遣**（普通人机也有 42%），暂无可靠判据。

## 九、踩坑记录（★ 都是真金白银换来的）

### 9.1 部署类

| 坑 | 现象 | 解法 |
|---|---|---|
| `cp` 覆盖被占用文件 | **静默失败**，以为部署了其实没有 | 必须 `cp 到临时文件 → mv -f`，并**打印 md5 校验** |
| 采集端进程名被抹 | `pkill -f` 抓不到 | 遍历 `/proc/*/exe` 按软链匹配 |
| adb shell 引号嵌套 | `unexpected EOF` | 一律写成 `.sh` 推到设备再 `sh` 执行 |
| 设备 shell 不支持 hex 运算 | `bad number` | 用 C 工具算，或在 adb 侧算 |

### 9.2 绘制端类

| 坑 | 现象 | 解法 |
|---|---|---|
| 系统字体创建失败 | `Assertion failed: src==nullptr && gDefaultTypeface==nullptr`，**进程秒死、Java catch 不住** | `textCN()` 里 `if(tfCN==null) return;`，文字改走图集 `gtext()` |
| esp.txt 字段写在别行 | 加密状态永远"未知"、undrawn 不显示 | 绘制端按**行首键名**解析，`enc3/undrawn/pdt` 必须**各自独立成行** |
| 音量键（114/115） | 面板神秘消失 | 是显隐开关，误触所致 |

### 9.3 逆向类

| 坑 | 教训 |
|---|---|
| 扫描只挑 `perm=='r'` 的段 | 代理位于 **37.9GB 的 `-w-p` 段**，整段被跳过 → "0 命中"是**假阴性** |
| 容差比较没排除 NaN | `fabsf(NaN-x)>1` 恒为 false → 满屏假阳性 |
| 只看 `0x614==23` 判特遣 | 自己/真人的 0x614 也是 23 → 真人被当成特遣 |
| 用 `ua==3` 排除自己 | 远端真人 ua 也是 3 → 会把人画丢；只能靠 `dm==0` |
| 只看 `t154==50` 认玩家 | 加密账号的远端真人可能是 `f154=24 + ua=2` |
| 外推窗口开太大会"飞" | 曾把窗口设到 4 秒（跟着最慢的代理走）→ 框满屏乱飞；现封顶 1.2s |

## 十、下一步建议（按价值排序）

1. **验证解密4 的实际跟随效果**，按手感调 τ（0.08~0.4 之间）。改 `g_tau` 一行即可。
2. **自动发现副本**：现在三通道是写死的偏移。可改为"玩家首次出现时在 proxy ±2MB 内扫一次，
   找到所有坐标副本，选更新最多的"——能覆盖偏移不固定的情况。
3. **护甲偏移**：需要一个"确定穿已知护甲"的队友做对照，`ARMOR` 候选见 docs/03。
4. **全图人数**：定位 `GameState.PlayerArray`。
5. **特遣识别**：需要用户指认 + ≥5 个普通人机做对照，才能标定。

## 十一、安全与合规

- 全程**只读内存**（`ioctl(P_READ_PHYS)`），**无写入、无断点、无执行流修改**。
- 采集端当前跑 300~400fps，**建议限流到 60fps**（ACE 会看读取频率）。
- 仅供安全研究/逆向学习，请勿用于破坏游戏公平性。
