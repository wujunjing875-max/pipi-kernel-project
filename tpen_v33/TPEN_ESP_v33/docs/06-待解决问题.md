## 1. 【最优先】坐标加密 —— 加密态下真人画不出来

### 现象

- 账号在某种状态下（被举报、设备环境异常时触发），**真人的世界坐标被加密**
- 表现：所有真人画出来挤在同一个点（常在地下）、骨骼缩成十几像素一坨
- **人机完全不受影响**（AI 不走网络同步，坐标一直是明的）

### 已知

| 项 | 结论 |
|---|---|
| 加密范围 | 只影响**真人**（`BP_UamCharacter_C`），AI / 盒子 / 物资都正常 |
| 自己是否受影响 | **不受**（RC 里 `isSelfObject` 走直读，不解密） |
| RC 的判定式 | `getFloat(actor + 0x47C) == 40.0f` ❌ **我们这版实测 `enc=0/N`，这个偏移不对** |
| 我们的 tf | `actor + 0x42C`，实测**所有角色恒为 40**（这是"类型"字段，不能当判据） |

### 实测数据（加密 / 不加密对比）

| 指标 | 不加密 | 加密 |
|---|---|---|
| 真人平均 Z | 2685~2991 | **-522** |
| 人机平均 Z | 2255~2701 | 516 |
| dz（两者差） | 291~414 | **1038** |
| zspan（真人内部跨度） | 808~1595 | **287** |

**当前判据**（`enc4`）：
```c
if (enN >= 3 && aiN >= 3)  enc4 = (dz > 500 && zspan < 600) ? 1 : 0;
else if (dz >= 0)          enc4 = (dz > 900) ? 1 : 0;
else                       enc4 = -1;
```
有效的，但**需要真人在场**（用户明确要求大厅/无真人也要能判）。

### RC 的解密链（可直接抄，但偏移要自己校准）

```c
// RC 源码 refence/内核源码/jni/include/主程序.h 620~640 行
Object    = r64(actor + 0x180);                       // RC 的 root，我们是 0x158
MyRootPtr = r64(r64(r64(Object + 0x118) + 0x0) + 0x90);
pos       = read 12 bytes at (MyRootPtr + 0x1160);     // ← 真坐标
```

RC 解密后还会做屏幕偏移修正（按距离 -240/-130/-60/-30 px），
说明解出来的值还差一点，需要一起复现。

### 建议方向

1. **先确定"加密开关"在哪**。强烈怀疑是腾讯 ACE 反作弊写的一个标记文件，
   见下面第 4 条。
2. 校准 `MyRootPtr` 链：对我们版本，把 `Object` 换成 `r64(actor+0x158)`，
   然后**扫 `+0x100 ~ +0x140`** 找那个中间指针（RC 是 +0x118）。
3. 验证方法：对加密中的真人，同时打印「旧坐标」和「按链解出来的坐标」，
   看后者是否和人机同量级、不重叠。

### 为什么难

- 加密是**账号级**的，触发不可控（要等被举报/环境异常）
- 已经有加密态的内存快照：`snapshots/enc_on/dump_enc_on.txt`（3 真人 + 3 人机 + 6 PlayerState）
  和 `dump_self.txt`（12 真人含自己），可以直接拿来对比

## 2. 护甲等级未找到（头盔已通）

### 现象

- **头盔**：`actor + 0x1f80` ✅ 准确（3头4甲→3，3头3甲→3）
- **护甲**：还没找到

### 已排除

```
❌ actor+0x1f84  恒为 4
❌ actor+0x1f94  恒为 4
❌ actor+0x1f64  恒为 4
❌ actor+0x1fac  恒为 4
❌ r64(armorMgr + 0x1D8)  → 0xffffffff（RC 的偏移不适用）
```

### 已验证的事实

- `actor + 0x1b38` / `+0x2008` 都是 `BPC_CharacterArmorManager_C` ✅
- 扫 `armorMgr + 0x0 ~ 0x500` 的指针，只有类引用（`BlueprintGeneratedClass`/`World`/`UADataTableManager`），**没有装备对象**

### 建议方向

1. **先确认前提**：远端玩家的护甲数据客户端到底有没有复制？
   方法：让一个**确定穿 4 甲**的队友站面前，dump 他的 actor，全扫有没有 `4`。
   如果扫不到，说明客户端不复制，这条路直接堵死（那就只能显示头盔）。
2. 如果确实有：用 `tools/uzi_dump.c` dump 两个不同护甲等级的真人，`diff_snapshot.py` 对比。

### 教训（重要）

> 曾经用「3头**4**甲」标定成功，以为找到了 `0x1f84`。
> 后来用户换成「3头**3**甲」，`0x1f84` 还是 4 —— 它就是个常量。
> **已知答案必须能让候选偏移互相区分**，否则标定无效。

## 3. 全图剩余玩家数不准

### 现象

顶部显示的「全图 N」其实是 **260m cull 范围内的真人数**，不是全场存活人数。

### 原因

客户端 260m 外的玩家**根本没有 actor**，靠遍历 Actor 数组数不出来。

### 正确来源

`GameState.PlayerArray`（TArray<APlayerState*>，服务器下发的全量玩家列表）。

### 已尝试（未成功）

```c
// 遍历时找类名含 "GameState"（不含 "PlayerState"）的 actor
for (og = 0x200; og < 0x500; og += 8) {
    读 TArray 结构：Data 指针有效 + 1<=Num<=100 + Max>=Num
    校验 r64(Data) 的类名含 "PlayerState"
}
```
**结果 `realpl=0`** —— 说明没找到匹配的 TArray，可能：
- GameState 的类名不含 "GameState"（比如叫 `BP_UamGameState_InBattle_C` 就含，但要确认）
- 或者 PlayerArray 的偏移不在 0x200~0x500
- 或者第一个元素不是 PlayerState

### 建议方向

1. 先 dump 所有**类名含 "Game" 的 actor**，看实际类名是什么
2. 对那个 actor 扫 `0x100 ~ 0x600`，把每个「指针 + 后面两个 int」的三元组打出来，
   人工找 `Num` 在 1~100 的 TArray
3. 也可以试试从 `world + 0x??` 直接找 GameState 指针（UE4 通常在 `UWorld::GameState`）

## 4. ACE 反作弊目录：疑似"加密开关"

### 发现

```
/data/data/com.tencent.mf.uam/files/ano_tmp/     ← 37 个 .dat
```

```
ace_cache_db.dat          ace_shell_db.dat        fake_uiui.dat
cache_crc.dat             cache_md5.dat           cpcah.dat
config2.dat.8e4d8896      config3.dat.b32da126    crt.i2.dat
kvcache8.dat              mn_cache.dat            rcu.ano.dat
tdm_cache.dat             tss_ano.dat             tme_firm.dat
ano.ano3.dat              ano.i.m.dat             ano_app_915c.dat
ano_ksh.dat               HANYCJLZOEUS_TOKEN2.dat SpeedUpCCH.dat
atti_obv.dat              bmc.dat                 h_rcd.dat
mpmc.dat                  comm.dat / comm.zip     ob_x.zip
tssmua.zip                mrpcs*.data             + ac_tmp/ custom_cache/ vm/
```

- `ace_*` = **ACE（Anti-Cheat Expert）**
- `tersafe` / `tss*` = TenSafe
- `ano_*` 一整套 = 某个检测模块

### 推测链条

```
ACE 检测到异常（被举报 / 环境可疑）
  → 往 ano_tmp/ 写标记
  → 游戏读到标记
  → 开始加密真人坐标
```

### 当前实现（`ace=N <文件名>`）

采集端每 2 秒 `opendir + stat` 这个目录，统计 5 秒内被写过的文件数。
**纯文件操作，完全不碰游戏内存**，所以不会增加被检测的风险。

### 待验证

- 正常运行 `ace=0`（启动期 18:43~18:53 写完后就不再动）✅ 已确认
- **加密时哪几个文件会变 —— 一次都没抓到过**

### 下一步（关键）

下次进入加密态时，扫一份这个目录的 md5：

```bash
adb shell 'su -c "cd /data/data/com.tencent.mf.uam && for f in files/ano_tmp/*; do md5sum \$f; done"' > snap_md5_enc.txt
```

和不加密基线（`snapshots/noenc_hot/snap_md5.txt`）对比，**变了的那个就是开关**。

一旦锁定，`ace` 通道就能**独立支撑「无真人也实时判断加密」**，满足用户要求。

## 5. 其他小问题

| 问题 | 说明 |
|---|---|

## 建议的推进顺序

1. **抓加密态文件快照** → 锁定 ACE 开关文件（最简单、收益最大）
2. 用锁定的文件 + 现有 `enc4` 判据，做出「无真人也能判」的加密检测
3. 校准 RC 的解密链 → 让加密态也能正常画真人
4. 确认远端护甲数据是否复制 → 决定要不要继续找护甲偏移
5. 定位 GameState.PlayerArray → 修全图人数
