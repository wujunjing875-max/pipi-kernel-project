# 02 · 驱动对接

> 采集端能读游戏内存，全靠一个**内核模块（LKM）**。
> 这份文档说明它怎么工作、怎么和采集端对接、测试机的 6 个内核版本怎么适配。

---

## 一、原理：hook `__NR_reboot`

Android 上的内核读写模块普遍用这招：hook `__NR_reboot` 这个系统调用。

```
用户态程序
   ↓ syscall(__NR_reboot, magic1, magic2, cmd, arg)
内核模块的 hook（先比对 magic1/magic2，不匹配就转发原函数）
   ↓ 匹配上了 → 执行 cmd 指定的操作（查进程 / 读内存 / 查模块基址…）
返回
```

**为什么用这个 syscall**：普通 App 不能直接用 syscall，必须经过 libc；
而 `reboot()` 在 libc 里是受 SELinux 限制的。直接用内联汇编发 `svc #0`
可以绕过 libc 包装，SELinux 对 raw syscall 的检查相对宽松。

采集端里的样子（`paradise_fast100.c`）：

```c
#define M1 0x7a3b9c4d
#define M2 0x2f8e1d6b

register long _x0 __asm__("x0") = (long)M1;
register long _x1 __asm__("x1") = (long)M2;
register long _x2 __asm__("x2") = (long)cmd;
register long _x3 __asm__("x3") = (long)arg;
register long _nr __asm__("x8") = __NR_reboot;
__asm__ __volatile__("svc #0" : "=r"(_x0) : "r"(_x0),"r"(_x1),"r"(_x2),"r"(_x3),"r"(_nr) : "memory","cc");
```

## 二、magic 与命令号

```c
#define M1 0x7a3b9c4d          // magic1
#define M2 0x2f8e1d6b          // magic2
#define CMD_INSTALL 0x1234567  // 0 号命令：分配 fd，返回值写回 arg 指向的 int

// 之后的 ioctl 都走这个 fd：
P_READ_PHYS   读内存（struct phys_io { pid, va, buf, size }）
P_FIND_PROC   按包名查 pid（struct find_io { name, pid }）
P_MODULE_BASE 查模块基址（struct mod_io { pid, name, base }）
```

**三段固定流程**（采集端 main 开头）：

```c
syscall(__NR_reboot, M1, M2, 0x1234567, &FD);   // 1. 拿 fd
if (FD >= 0) fcntl(FD, F_SETFD, FD_CLOEXEC);    //    别让子进程继承
ioctl(FD, P_FIND_PROC, &fi)                     // 2. 找游戏 pid
ioctl(FD, P_MODULE_BASE, &mo)                   // 3. 拿 libUE4.so 基址
```

## 三、驱动文件是「自包含」的

`drivers/drv_61.sh` 这类脚本**不是**引用外部 .ko，而是把 ko 用 base64 内嵌在脚本里：

```sh
#!/bin/sh
set -e
TMP=$(mktemp)
trap "rm -f $TMP" EXIT INT TERM
base64 -d <<'__EMBEDDED_KO_B64__' > "$TMP"
f0VMRgIBAQAAAAAAAAAAAAEAtwABAAAAAAAA...   ← 整段 base64
__EMBEDDED_KO_B64__
insmod "$TMP"
...
```

**好处**：一个文件就能刷驱动，不用管 ko 放哪、不用担心 ko 被 `ls` 看到。

**用法**：

```bash
adb push drivers/drv_61.sh /data/local/tmp/drv.sh
adb shell 'su -c "sh /data/local/tmp/drv.sh"'
# 成功输出 ok，失败输出「驱动加载失败」+ dmesg
```

## 四、6 个内核版本怎么选

| 脚本 | 内核版本 | 大小 |
|---|---|---|
| `drv_510.sh` | 5.10 | 430 KB |
| `drv_515.sh` | 5.15 | 465 KB |
| `drv_61.sh` | **6.1** | 463 KB |
| `drv_66.sh` | 6.6 | 373 KB |
| `drv_612.sh` | 6.12 | 428 KB |
| `drv_618.sh` | 6.18 | 403 KB |

**怎么知道该用哪个**：

```bash
adb shell 'uname -r'
# 例：6.1.118-android14-O64646   → 取 major.minor = 6.1 → 用 drv_61.sh
```

APK 里的「智能刷入」就是干这个的：

```java
// System.getProperty("os.version") 失败就退回 uname -r
// 匹配顺序：精确 → 同 major 不超过它的最大 → 全局不超过它的最大 → 最近的
```

**踩过的坑**：内核小版本对不上时 `insmod` 会失败并报 `Invalid module format`
（vermagic 不匹配）。这时候只能换一个更接近的版本试，或者自己编译对应内核的 ko。

## 五、驱动是**独占式**的

这是最容易踩的坑：

- 驱动同一时刻只能被**一个进程** attach（拿 fd）
- 后来者 `syscall` 拿不到 fd，或者 `ioctl(P_FIND_PROC)` 直接失败

**表现**：采集端启动后立即退出，`p.log` 里只有一行 `no pid`，
`esp.txt` 不再更新，但绘制端还在画**上一帧的旧数据**——
看起来像「绘制没坏，但数据不动了」。

**实测案例**：RC 的 `UziUam.rc` 也走 reboot hook（它的 magic 是 `0x114514/0x1919810`），
跑起来之后我们的采集端就 `no pid` 了，屏幕上只剩 RC 在画。

**处理**：
1. `kill -9 <抢占者>`
2. 往往还需要**重启设备**（驱动被弄脏后重新 insmod 不一定恢复干净）

## 六、自研驱动要注意

如果你要自己编译/修改 ko：

1. **必须匹配目标内核的 vermagic**（`uname -r` 的完整字符串）
2. **hook 点选择**：`__NR_reboot` 是最常见的，也有用 `__NR_prctl`、io_uring 的
3. **多 magic 共存**：hook 里可以先比对多个 magic 集合，这样能同时兼容多套工具
4. **反检测**：模块名、`/proc/modules` 可见性、syscall 表还原程度都会影响检测
5. **隐藏模块**：需要 hook `module_kset` 或直接摘链表（有的内核有 `list_del` 保护）

**注意**：`lsmod` 里看不到模块 **不等于** 模块没加载——
测试机上 paradise 模块就没出现在 `lsmod`（被隐藏了），但采集端能正常读写内存。

## 七、部署后自检清单

```bash
# 1. 模块是否真的在（lsmod 看不到也正常，用功能验证）
adb shell 'su -c "cd /data/local/tmp && ./p; echo EXIT=$?"'
#    期望：不打印 no pid / no base，而是开始写 esp.txt

# 2. fd 拿到没有（调试版会打印）
#    正常 FD 是一个小整数（如 4、7）；-1 表示 syscall 没被 hook 命中

# 3. 关键三项
adb shell 'su -c "head -4 /data/local/tmp/esp.txt"'
#    pid=<游戏pid>  ← 对得上
#    cnt=<1000~2000> ← Actor 数量正常
#    local=<非0,0,0>  ← 本地坐标读到了
```

如果 `cnt` 很小（几十）或 `local=0,0,0`，通常是游戏还在加载界面，等进到大厅就有了。
