# 05 · 踩坑记录

> 每一条都是**真实踩过、花了时间才找到**的。按「症状 → 原因 → 解决」写，方便对照。

---

## A. 编译 / 打包类

### A1. `d8` 报 `Invalid output: build\dex`

**症状**：打包失败，说 `build\dex` 不存在或者不是 zip/dir。但脚本明明 `mkdir -p` 过。

**原因**：`rm -rf build` 删除的文件数超过 20，被**安全删除策略静默拦截**。
脚本不报错，但 build 没清掉；`javac -d build/jcls` 只自动创建了 jcls，
dex 目录状态就乱了。

**解决**：
```sh
mkdir -p build/jcls build/dex
find build -name '*.class' -delete 2>/dev/null || true
find build -name '*.dex'   -delete 2>/dev/null || true
# 永远不要 rm -rf 整个 build
```

---

### A2. 改了 `.sh` 之后脚本行为诡异

**症状**：`rm -rf build` 实际删的是 `build\r`，各种路径找不到。

**原因**：Windows 上 Python `io.open(path, 'w')` 默认 **newline 转换**，
把 `\n` 写成 `\r\n`。shell 脚本里每行末尾都多个 `\r`。

**解决**：
```python
io.open(p, 'w', encoding='utf-8', newline='')   # Python 侧
```

```bash
sed -i 's/\r$//' xxx.sh                        # shell 侧再兜一刀
```

**这是本项目最高频的坑，改任何 `.sh` 都要补一条 `sed`。**

---

### A3. clang 找不到临时目录 / 编译莫名失败

**原因**：Windows 下 `TEMP`/`TMP` 指向含空格或中文的路径。

**解决**：`TEMP=/d/tmp TMP=/d/tmp clang ...`

## B. 内存读取类

### B1. 写了个 dump 工具，一个 actor 都读不到

**症状**：`cnt=1600` 读到了，但 `np=na=nps=0`（一个都没匹配）。

**原因**：**忘了初始化 `GN`（GNames 基址）**。
`cls_name()` 依赖全局 `GN` 去查 FName 表，`GN=0` 时所有类名解析都失败。

**解决**：
```c
uint64_t base = mo.base;
GN = base + GOFF_GNAMES;      // ← 必须在调用 cls_name 之前
```

**同时两个小坑**：
- `cls_name(actor, out, cap)` 传的是 **actor 地址**，不是 class 指针（内部自己取）
- `disguise(argc, argv)` 会清掉 argv，**参数要先 strcpy 到本地 buffer**

---

### B2. 遍历 Actor 数组，逐个 `r64(actors + i*8)` 全部读到 0

**原因**：驱动的单次读对「非对象指针地址」有限制，逐 8 字节读数组元素会失败。

**解决**：**一次性批量读**整个数组：
```c
static uint64_t BUF[4096];
int nn = (rd(actors, BUF, (uint64_t)cnt * 8) == 0) ? cnt : 0;
for (int i = 0; i < nn; i++) {
    uint64_t a = BUF[i] & 0x00ffffffffffffffULL;
}
```

---

### B3. 采集端启动就退出，`p.log` 只有一行 `no pid`

**原因（最常见）**：**驱动被别的进程抢占了**（驱动是独占的）。
典型场景：同时跑了 RC 的 `UziUam.rc`。

**排查顺序**：
1. 游戏是否真的在跑？`pidof com.tencent.mf.uam`
   （游戏没启动时也是 `no pid`，这是最容易被忽略的）
2. 有没有别的 ESP 在跑？`ps -A | grep -iE "uzi|rc$"`
3. 驱动 fd 拿到没有？临时加一行 `fprintf(stderr, "FD=%d\n", FD)`，
   正常是个小整数，`-1` 说明 syscall 没被 hook 命中

**解决**：`kill -9` 抢占者；不行就**重启设备**（驱动可能被弄脏）。

## C. 游戏数据判定类（最容易犯逻辑错误）

### C1. 以为 `0x1290 == 3` 是「本地自己」

**症状**：附近明明有真人，ESP 一个都不画。

**原因**：`ua==3` **不只是自己**。实机抓到同一帧 4 个 `BP_UamCharacter_C`：
两个 ua=2、两个 ua=3，全在 85~90m，都是有 PlayerState 的真玩家。
用 `ua==3` 排除自己，把他们一起排掉了。

**解决**：排除自己只能用 **`dm == 0`**（和本地 RootComponent 完全重合）。
敌人不可能和你在同一个坐标。

**教训**：14:04 那次只抓到一个 `d=0 ua=3` 的对象就下了结论。
**样本只有 1 个就归纳，是这类错误的根源。**

---

### C2. 用 `tf == 40.0f` 当「是玩家」的判据

**症状**：屏幕上冒出几十个「玩家」，人数统计到 51。

**原因**：`SGPooledImpactEffect`（弹着特效）、`BP_GFGashapon_*`（扭蛋机）
这些杂项的 tf **也恒为 40**。一次能塞进 29 个假玩家。

**解决**：兜底判据必须极严——
**有效骨骼网格 + 骨骼数 ≥ 20 + PlayerState ≠ 0** 三条同时成立。
另外「类名认出来了但不含 Character/Pawn」的一律丢弃。

---

### C3. 头甲偏移标定「成功」了但其实是巧合

**症状**：用户 3头3甲 时读 `h=3 a=3`，看起来完全正确；换 3头4甲 后读 `h=3 a=3`，还是"对"。

**原因**：**两个候选偏移的值刚好相同**（都是 3），根本区分不出哪个是头哪个是甲。
错误的那个也"碰巧对了"。后来发现 `0x1f84` / `0x1f94` 是**常量 4**，
只是因为用户那天刚好穿 4 甲，才看起来吻合。

**解决 / 教训**：
> **用已知答案标定偏移时，已知值必须能让候选偏移互相区分。**
> 「3头3甲」这种两个值相同的情形，等于没标定。
> 必须换一组**不同的值**（比如 3头4甲）再验一次。

**当前状态**：`0x1f80` = 头盔 ✅；**护甲仍未找到**。

---

### C4. 把「穿在身上的装备 actor」当成地上物资画

**症状**：满屏「悬空的 KIRASA 防弹衣 / SSh68 头盔」，位置还在没人的地方。

**原因**：`BP_Vest_Kirasa_C` / `BP_Helmet_SSh68_C` 是**装备本体**，
不是可拾取物。它们的 RootComponent 坐标不可靠。

**解决**：地面物资必须含 **`_Uam_C`** / `ItemBase` / `_Item`：

```
地面可拾取：BP_9x19mm_PSO_gzh_Uam_C      ← 带 _Uam_C
装备本体  ：BP_Vest_Kirasa_C             ← 不带，丢弃
```

再加一层「与任何角色距离 < 2m 就跳过」，防止穿着装备被单独画。

---

### C5. 大厅的展示人机被 `continue` 掉了

**症状**：大厅里那个会动、有骨骼的展示单位不见了。

**原因**：它是 `BP_UamCharacterTemplate_Preview_C`，
`ua` 也是 3、`bones` 也是 109，字段上和真角色一模一样，
只能靠类名里的 `Template`/`Preview` 区分。之前为了不让它在对局里被误判成真人，
直接 `continue` 丢弃了。

**解决**：不要丢弃，改成「要画，但不算真人」：
```c
if (isTmpl) kind = (r64(actor + 0x330) != 0) ? 0 : 1;   // 有 PlayerState=真人，否则=人机
```

## D. 绘制类

### D1. 转视角时容器拖出一串叠影

**症状**：静态看正常，一转头就看到箱子拖影。

**原因**：防闪烁缓存的 key 里带了**屏幕位置格**：
```java
String key = k + "|" + inst + "|" + name + "|" + Math.round(txtX[i]/45f);  // ❌
```
转视角时同一个箱子每帧坐标都在变 → 每帧生成新 key →
600ms 内堆了十几个副本 → 全部补画 → 一串叠影。

**解决**：key **绝对不能带屏幕位置**，用「类型+实例名+类名」，位置每帧就地更新。
保留时间也从 600ms 降到 250ms，补画一次就标过期。

---

### D2. 进对局一小会就「闪退」

**症状**：大厅正常，进对局几秒后整个 overlay 消失。

**原因**：`keepAlive()` 里
```java
boolean[] seen = new boolean[pvN];   // ← 按「当前条数」开
...
if (hit < 0) { hit = pvN++; ... }    // ← pvN 在这个循环里增长
for (int j = 0; j < pvN; j++) seen[j];  // ← 越界！
```
大厅容器少（pvN=0~1）撞不上；进对局容器一多，第一次增长就 `ArrayIndexOutOfBounds`，
异常冒泡把绘制线程干掉。

**解决**（三重保险）：
1. `seen` 固定 `new boolean[256]`
2. 循环加 `j < 256` 和 null 判断
3. **整个函数 + 整个主循环都包 try/catch**

```java
for (int f = 0; ; f++) {
  try {
      ... 整帧绘制 ...
  } catch (Throwable th) {
      System.out.println("[!] frame " + f + " 异常(已吞掉继续画): " + th);
      try { Thread.sleep(50); } catch (Throwable t2) {}
  }
}
```

> **主循环没有 try/catch = 任何单帧异常都会导致「闪退」。这是最值钱的一条经验。**

---

### D3. 英文名字糊成一团

**原因**：字形图集里每个字形都是 **30×34 的单元格**，但 ASCII 字符的 advance 只有 8~11。
按单元格宽画，字母互相压住。

**解决**：
```java
int dw = (g[4] < 20) ? (g[4] + 2) : g[2];   // 窄字符用 advance 当绘制宽度
```

---

### D4. 一整片区域的标注在闪

三个独立原因，都修了：

1. **绘制距离压在 cull 边界**：客户端 cull ≈ 260m，原来画到 260m，
   边界上的物件每帧存在性不同 → 整片闪。改成角色 250m / 容器物资 120m。
2. **`loadEsp()` 读失败时标签已被提前清空**：采集端是「写 tmp → rename」，
   绘制端 `new FileReader` 撞上 rename 瞬间会 ENOENT。
   原来清空动作在 `loadEsp()` **之前**，读失败就整帧空白 → 闪一下。
   **改成「文件打开成功之后才清空」**。
3. **streaming 抖动**：加 `keepAlive()` 600ms 保留（但注意 D1 的 key 陷阱）。

---

### D5. 头甲重复杂乱

**原因**：角色主标签写了 `名字 头3 甲3`，下面「武器行」本来就写着 `头3 甲3 包X 武器`。

**解决**：主标签只留 `名字 距离M`，头甲只在武器行显示一次。

## E. 工程 / 环境类

### E1. 刷机/重置后全没了

`/data/local/tmp` 会被清空。恢复清单见 `README.md`「快速开始」。

**注意**：`drivers/drv_*.sh` 是自包含的（base64 内嵌 ko），
推一个文件就能加载驱动，不需要单独找 `ko`。

---

### E2. push 到 `/data/local/tmp/.c/` 报 `Permission denied`

**原因**：`.c` 是 root 的 0700 目录，`adb push` 以 shell 身份写不进去。

**解决**：先 push 到 `/data/local/tmp/`，再 `su -c "cp ..."`。

---

### E3. `su -c "nohup xxx &"` 说启动了但没有进程

**原因**：su 退出时会连子进程一起收掉。

**解决**：
```sh
setsid sh -c "exec xxx > log 2>&1" < /dev/null &
```

---

### E4. 数组扩容后忘了改初始化循环

**症状**：第 33 个以后的容器分类全错，全显示成「玩家盒子」。

**原因**：标签数组从 32 扩到 128，但初始化循环还写着 `for (i = 0; i < 32; i++)`。
索引 32~127 的 `txtType` 默认值是 0，而 0 恰好是「玩家盒子」的类别。

**教训**：改数组容量时，**所有** `i < 32` 的地方都要一起改（初始化、边界检查、打印）。

## F. 方法论类的（比代码更重要）

### F1. 别用行为推断代替字段判定

做过一版「多个真人坐标挤在一起 → 判定加密」。
问题是：**没真人时判不了**（用户明确否决了）。

**默认优先找字段级证据**，行为推断只能当辅助。

### F2. 报错要捞到「第一现场」

- 采集端：`p.log`（stderr 重定向）
- 绘制端：`o.log` + 每帧异常都会被打印
- 驱动：`drv.log` + `dmesg | grep -i paradise`

**没有日志的调试 = 猜。** 每次改代码都先确认日志能打出来。

### F3. 改动要能「一眼验证」

每加一个诊断，都设计成能直接看出对错的格式，例如：

```
SELF_LA h=3 a=4        ← 一眼看出护甲可能是常量
zmin=-611 zmax=-441 zspan=170  ← 一眼看出分布正常/异常
cnt=1641 nn=1641 np=3 na=3     ← 一眼看出遍历成功但类名没匹配
```
